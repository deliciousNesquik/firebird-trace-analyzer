# Кэширование парсинга: `ParsingContext`

Контекст одного разбора — набор пулов **интернирования** (дедупликации ссылок) на время одного
прохода парсера. Схлопывает многократно повторяющиеся строки и объекты в единственные экземпляры,
чтобы результат разбора большого трейс-файла не раздувал память.

Живёт в проекте **`FirebirdTraceParser`** (без зависимостей от UI).

---

## 1. Анализ предметной области (зачем это нужно)

Трейс-файлы Firebird — **большие** (сотни МБ, сотни тысяч событий в одном файле) и **крайне
повторяющиеся**:

- один и тот же **SQL-запрос** выполняется тысячи раз → тысячи событий несут идентичный текст;
- одно **подключение** (attachment: путь к БД, пользователь, роль, charset, протокол, адрес…)
  фигурирует во множестве событий;
- **типы/имена параметров** (`param0`, `bigint`, …), имена компонентов, сообщения ошибок,
  имена процедур/триггеров, названия таблиц в perf-статистике — повторяются массово.

Если парсить «в лоб», каждое событие держало бы **свои копии** этих строк и объектов. На большом
файле это даёт кратный перерасход памяти и давление на GC.

**Решение — интернирование в пределах разбора:** все равные строки приводятся к одному экземпляру,
все события одного подключения/сессии ссылаются на один `AttachmentInfo`/`TraceSessionInfo`.
Событий по-прежнему много, но **уникальных строк/объектов — мало**, и все ссылаются на них.
Парсер уже интернирует — это же прямое доказательство сильной повторяемости, на которой строится
и кросс-файловый дедуп в хранилище (см. §6).

## 2. API

| Член | Назначение |
|---|---|
| `string Intern(string? value)` | дедуп строки в пределах разбора; `null`/пусто → `string.Empty` |
| `bool TryGetAttachment(long attachmentId, out AttachmentInfo?)` | получить ранее собранный `AttachmentInfo` по id подключения |
| `AttachmentInfo AddAttachment(AttachmentInfo info)` | положить `AttachmentInfo` в пул (ключ — `AttachmentId`) и вернуть его |
| `TraceSessionInfo InternSession(int sessionId)` | вернуть существующую или создать новую `TraceSessionInfo` по id сессии |

Внутри — три обычных `Dictionary`: `string→string`, `long→AttachmentInfo`, `int→TraceSessionInfo`.

---

## 3. Жизненный цикл

- Создаётся **заново на каждый разбор** в `TraceLogParser` — во всех трёх точках входа:
  `ParseFile`, `ParseFileAsync`, `ParseStreamAsync` (`var context = new ParsingContext();`).
- Прокидывается параметром `context` по всей цепочке разбора и **живёт только до конца этого
  разбора**; по завершении — вместе со всеми пулами уходит в GC.
- **Не статический** → парсер **реентерабелен и параллелизуем** (регистрируется `Transient`,
  разные файлы можно разбирать одновременно), ручной `Reset()` не нужен, межфайлового «загрязнения»
  пулов нет.

---

## 4. Что и где дедуплицируется

Контекст проходит `TraceLogParser → IEventHandler → DefaultEventHandler → PerformanceTableParser`.
Конкретные точки:

| Что | Через | Где (примеры) |
|---|---|---|
| `HexTraceId` | `Intern` | заголовок события |
| Поля подключения: `DatabasePath`, `User`, `Role`, `Charset`, `Protocol`, `Address`, `ProcessPath`, `"<internal>"` | `Intern` + `Add/TryGetAttachment` | `DefaultEventHandler` (сборка `AttachmentInfo`) |
| `Component`, сообщения ошибок | `Intern` | событие ошибки |
| Параметры SQL: `Name`, `Dtype`, `Value` | `Intern` | разбор параметров |
| Текст `Sql`, `ProcedureName`, имя/таблица/тайминг/событие триггера | `Intern` | statement/procedure/trigger |
| `TableName` в perf-статистике | `Intern` | `PerformanceTableParser` |
| Подключение целиком (`AttachmentInfo`) | `TryGetAttachment`/`AddAttachment` по `AttachmentId` | все события одного коннекта делят один объект |
| Сессия (`TraceSessionInfo`) | `InternSession` по `SessionId` | события одной сессии делят один объект |

---

## 5. Почему именно так (проектные решения)

- **Пер-разбор, а не статика/глобальный кэш.** Статический пул пришлось бы синхронизировать
  (парсер параллелится), он рос бы неограниченно и смешивал бы данные разных файлов. Пер-разбор —
  ограниченное время жизни, освобождается с разбором, без блокировок.
- **Обычный `Dictionary`, а не `ConcurrentDictionary`.** В пределах одного разбора доступ
  **однопоточный** (один контекст = один проход) → синхронизация не нужна, `Dictionary` быстрее.
- **Свой пул, а не `string.Intern` (CLR).** Пул интернирования CLR — **глобальный на процесс и
  никогда не освобождается**: интернировать туда временные данные трейса = утечка на всё время
  жизни процесса. Свой `Dictionary` уходит в GC вместе с разбором.
- **Дедуп подключений/сессий по id, а не по значению.** В трейсе подключение задаётся один раз и
  далее адресуется по `AttachmentId`/`SessionId` — поэтому ключ пула — id, а не сравнение полей.

---

## 6. Связь с дедупом хранилища

Интернирование здесь — **в памяти и в пределах одного файла**: строка, повторяющаяся в разных
файлах, в памяти не разделяется. Кросс-файловую дедупликацию делает уже **`EventStore`** на диске
(таблицы `sql_text`/`attachment` с `UNIQUE(sha)`). Механизмы **дополняют** друг друга:

- `ParsingContext` — снижает пик памяти при разборе одного файла;
- `EventStore` — снижает размер архива за счёт общих строк между файлами.

---

## 7. Как расширять

- Новый вид часто повторяющейся строки при разборе → оборачивать в `context.Intern(...)` в месте
  сборки события (в `DefaultEventHandler`/`PerformanceTableParser`), а не хранить сырую строку.
- Новый повторяющийся составной объект (по аналогии с attachment/session) → добавить в контекст
  пул `Dictionary<ключ, T>` + метод `Intern…`/`TryGet…`, ключевать по стабильному id.
- Не превращать `ParsingContext` в статику и не заводить блокировки — это сломает реентерабельность.
